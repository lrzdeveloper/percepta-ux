# Product context: establish what must remain true

Read this for a new surface, redesign, cross-platform change, or conflicting project
guidance. A narrow edit can use the surrounding code and known brief directly.

## Resolve the brief from evidence

Use explicit user choices first. Inspect relevant product/design notes, existing
tokens and components, neighboring screens, and the actual target. Reuse the
project's terminology. Record only decisions that change the work: audience and
goal, platform and inputs, frequency/consequence, existing visual commitments,
real content/assets, and the requested scope of change.

A file named DESIGN.md can be useful, but its name does not make stale content
more authoritative than the current project. When notes and implementation differ,
identify the conflicting rule and consequence. Follow a clear user instruction;
otherwise clarify a material conflict or state a bounded assumption. Report stale
notes without rewriting unrelated project documentation as a side effect.

Missing context files do not imply a new product. Continue from the available
brief and incumbent interface. Create a persistent brief or design record only
when requested or required by the repository, using its existing convention.

## Choose what this surface must do

Prioritize the task rather than importing a look from a different surface. A
frequent operational task benefits from stable controls and useful density; a
reading task needs comprehension and navigation; a purchase needs comparable
terms and informed commitment; exploration can allow more expression. One product
can contain several of these. Treat a real app fragment inside a marketing page
as an interface with its own task and state, while maintaining shared identity.

Separate preservation from replacement. A refinement improves the current system.
An authorized redesign can replace visual decisions while retaining product facts,
URLs and commitments, meaningful functionality, and platform expectations unless
changing them is part of the brief. Make a material behavioral change explicit.

## Build with available material

Use real content and assets. If an asset or service is missing, adapt the proposal
to what exists and name the gap. Sample content must be clearly identified;
evidence, testimonials, performance, prices, availability, and transaction outcomes
require real support. Do not make a polished mockup imply an implemented service.

For a substantial design, keep a short working contract: the desired outcome,
constraints to preserve, proposed intervention, authoritative success state, and
check that would demonstrate it. It can stay in the response or working notes.
Reuse it during verification rather than reopening settled choices at every step.
